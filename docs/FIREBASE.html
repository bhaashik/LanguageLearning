Use Gemini through Firebase

Keep Bhaasa on GitHub Pages and deploy only its model gateway to Firebase Cloud Functions. The same HTTPS gateway can serve the browser, Linux, Windows, Android, and iOS versions. Start with your browser; no change to GitHub Pages hosting is needed.

Flow: Bhaasa → your HTTPS Firebase function → Gemini Developer API. The Gemini key stays in Google Secret Manager. Enabling an API or creating a Firebase web app does not deploy these Bhaasa endpoints.

If Firebase AI Logic says “Unregistered”

For an existing web app such as bhaashik-web-gateway, first check the column/label: App Check → Unregistered means the app has not registered an attestation provider. The app itself can already be registered with Firebase. Go to Firebase Console → App Check → Apps, select the existing web app, and choose reCAPTCHA Enterprise. Create a website key in Google Cloud’s reCAPTCHA console, allow bhaashik.github.io (no scheme or repository path), and register its key ID in App Check. The public reCAPTCHA website key is different from the private Gemini API key. See Firebase’s web App Check guide.

Keep App Check enforcement off until the client SDK sends valid tokens. Bhaasa does not currently include Firebase AI Logic or App Check client SDKs. Registering the app/provider alone cannot connect it. Using AI Logic’s managed proxy directly requires that client integration, Firebase web configuration, and App Check setup; it is a different route from the Cloud Functions template below.

The template below is an optional bridge for Bhaasa’s existing gateway protocol and requires Blaze billing. It does not use Firebase AI Logic’s managed proxy and does not require App Check registration. Its separate gateway token protects requests; Firebase AI Logic enforcement does not protect a custom Cloud Function automatically. You do not have to register a second Firebase web app or turn on Firebase Hosting to use this bridge.

This template is for your initial private testing. It requires a separate gateway access token on every configuration/generation request. CORS alone does not control API spending. Share that token only with trusted testers. For wider distribution, add per-user authentication, rate limits/quotas, and abuse protection; Firebase AI Logic/App Check is a separate possible integration, not something this template automatically enables.

1. Prepare your Google project and key

  1. In Firebase Console, open your project. Under Project settings → General, copy the Project ID, not the app ID or project display name. Use that ID wherever YOUR_PROJECT_ID appears below.
  2. Link a billing account / use the Blaze plan to deploy Cloud Functions. Cloud Functions, build/artifact storage, Secret Manager, network traffic, and Gemini have their own pricing/allowances. A Gemini API free tier does not guarantee free Firebase hosting of the gateway. Set a billing budget alert and suitable Gemini project quotas; an alert does not cap spending.
  3. In Google AI Studio → API keys, select/import this existing Google Cloud project and create a Gemini Developer API key for the backend. Confirm the Generative Language API is enabled for that project in Cloud Console. Google Cloud Vision API and Vertex AI are different integrations.
  4. In Cloud Console → APIs & Services → Credentials, restrict this backend key to the Generative Language API where supported. Browser HTTP-referrer restrictions will reject requests from a server. Ordinary Functions egress has no fixed IP for an IP restriction without additional networking configuration.

A Firebase web app’s public firebaseConfig.apiKey, an OAuth client ID, and a Google chat subscription are not substitutes for this server key. This integration uses an API key, so you do not need an OAuth JavaScript origin, redirect URI, Firebase web SDK, or a registered Firebase web app. If you enabled Firebase AI Logic, Bhaasa still needs this gateway or a separate AI Logic client integration.

2. Deploy the gateway

Use a terminal on your computer with Git and Node.js 22, or Google Cloud Shell with that Node version. Deployment must run under a Google account allowed to deploy Functions and manage project secrets. You do not need a GitHub Actions service-account key.

git clone https://github.com/bhaashik/LanguageLearning.git
cd LanguageLearning
npm ci --prefix firebase/functions
npm install -g firebase-tools
firebase login
cd firebase

If already cloned, update your checkout instead of cloning it again. In Cloud Shell or a remote terminal, use firebase login --no-localhost if ordinary login cannot open its browser callback. No localhost URL goes into the production endpoint.

Store the Gemini key interactively. Paste it only at the CLI’s secret prompt:

firebase functions:secrets:set BHAASA_GEMINI_API_KEY --project YOUR_PROJECT_ID

Generate a different random gateway access token on your own computer/Cloud Shell, save it in your password manager, then paste it into the second secret prompt:

node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
firebase functions:secrets:set BHAASA_GATEWAY_TOKEN --project YOUR_PROJECT_ID

The second token is what you enter in Bhaasa. The Gemini key is never entered there. Do not commit either secret, put it in an endpoint URL, or paste it into chat.

Copy firebase/functions/env.example to firebase/functions/.env.YOUR_PROJECT_ID using your editor. Because you are now in the firebase directory, the relative paths are functions/env.example and functions/.env.YOUR_PROJECT_ID. Keep only nonsecret settings in that file:

BHAASA_ALLOWED_ORIGINS=https://bhaashik.github.io,http://127.0.0.1:4173,http://localhost:4173
BHAASA_OCR_GEMINI_MODEL=gemini-2.5-flash
BHAASA_ASR_GEMINI_MODEL=gemini-2.5-flash
BHAASA_TTS_GEMINI_MODEL=gemini-2.5-flash-preview-tts
BHAASA_TTS_GEMINI_VOICE=Kore

These model IDs are examples supported by Bhaasa’s adapters, not a promise of current availability or free quota. Use exact IDs available to your project: OCR needs image input and JSON output; ASR needs audio input and JSON output; TTS needs audio output. A generic Gemini label or image-generation model is not interchangeable. Keep a single exact ID per variable in this template.

The template uses us-central1, zero minimum instances, at most two instances, two concurrent requests per instance, 512 MiB RAM, and a 120-second function timeout. Edit functions/index.mjs before first deployment if another supported region is needed. Region/model availability and provider terms still apply. Instance limits are not a spending cap.

firebase deploy --only functions:bhaasa --project YOUR_PROJECT_ID

The bhaasa selector deploys this template’s codebase; it does not deploy Firebase Hosting or unrelated codebases. Accept required API-enablement prompts only for your intended project. If the CLI reports missing deployment permissions or billing, resolve those in that project; enabling Gemini alone is insufficient.

Copy the exact Function URL printed for bhaasaApi. It can be a cloudfunctions.net URL or a Cloud Run .run.app URL. Use what the CLI prints; do not construct a URL from the Firebase app ID.

Example base URL:

https://us-central1-YOUR_PROJECT_ID.cloudfunctions.net/bhaasaApi

The Google HTTP invoker is public so a browser can reach it. The function itself requires your separate token; it rejects missing/wrong tokens before model discovery or Gemini generation. If your organization forbids public HTTP invokers, this template needs an approved authentication design before it can be used.

3. Connect the browser app

  1. Open the updated Bhaasa web app → Connections & models. If the Private test gateway access section is absent, reload the updated app or pull and run the latest source locally.
  2. Set OCR to Google Gemini, TTS to Google Gemini, and ASR to Google Gemini audio.
  3. Paste your function base URL into Optional gateway base URL. Click Fill the three gateway addresses.
  4. Expand Private test gateway access, enter the separate BHAASA_GATEWAY_TOKEN value, and click Save access for this session. Never enter BHAASA_GEMINI_API_KEY here. The access token is scoped to this exact gateway’s API routes and stored for this tab/session, including reloads, rather than in progress/audio exports.
  5. For each of OCR, TTS, and ASR, click Discover gateway models, select a configured model, and click Use these settings. For TTS choose the reported Kore voice, or an exact supported voice ID. Configure Malayalam and French voice/ASR preferences separately when switching languages.
  6. Try one handwriting recognition, one Listen action on a phrase, and one short recorded speaking check. Discovery alone reads server configuration; it does not prove Gemini authorization, modality support, quota, or recognition quality.
PurposeAddress relative to function baseModel example
OCR / handwriting/api/ocrgemini-2.5-flash
TTS / listening/api/speech (model list: /api/speech/models)gemini-2.5-flash-preview-tts
ASR / speaking check/api/transcribegemini-2.5-flash

These are your Bhaasa gateway URLs, not Google’s generativelanguage.googleapis.com endpoint. Opening a protected URL in another browser tab ordinarily shows gateway_access_required: that navigation has no token header. Use Bhaasa’s Discover buttons after saving access.

4. Use the same gateway on other platforms

The web app, desktop packages, and Capacitor mobile apps share the request format. Each device needs its own connection settings and access token. Native packages must be rebuilt from a source version containing the access-token controls; the older v0.7.1 test downloads do not have them. On an iPad/iPhone, use the updated web app meanwhile.

Add the exact client origins you need to BHAASA_ALLOWED_ORIGINS, separated by commas, then redeploy. An origin has no page or repository path. Typical values for this repository are:

# Hosted browser / installed PWA:
https://bhaashik.github.io
# Local browser development:
http://127.0.0.1:4173
http://localhost:4173
# Linux/Windows desktop, default port:
http://127.0.0.1:4174
# Android Capacitor WebView:
https://localhost
# iOS Capacitor WebView:
capacitor://localhost

Keep the gateway address HTTPS on every device. The native app’s https://localhost origin identifies its packaged page; it is not the gateway URL. Use the actual browser origin if a desktop port or hosting domain changes. There is no need for one provider key per operating system.

5. Changes and troubleshooting

  • Change model/voice/origins: edit functions/.env.YOUR_PROJECT_ID, then redeploy functions:bhaasa. Rediscover models and update the corresponding saved app settings; a saved explicit old model remains explicit.
  • Rotate a key/token: rerun its functions:secrets:set command, then redeploy so the function binds the new secret version. After rotating the gateway token, forget old session access and enter the new token in Bhaasa.
  • HTTP 401 / gateway_access_required: save the gateway token for the exact function base URL. Changing between a Cloud Run URL and a Functions URL also changes its scope. Do not fix this by removing authentication.
  • CORS/network failure: verify the exact app origin is allowed and redeployed. Use the HTTPS function base, including /bhaasaApi if present, with the three API suffixes. GitHub Pages and your Firebase site URL do not automatically provide these APIs.
  • HTTP 403: distinguish Google IAM/invoker or organization policy from the function’s origin_not_allowed and Gemini key/API-access errors. The Google key must belong to the enabled project and permit the Generative Language API.
  • HTTP 400/404 from Gemini: verify the exact model exists for the project and supports the required input/output. The optional List models from Gemini control in tracing reads Google’s catalogue using the server key, but does not test OCR/TTS/ASR generation.
  • HTTP 429: inspect quota/billing for the selected Gemini model. 502/503/504: inspect Functions logs and provider availability/model output. Retry explicitly; failed requests do not receive a learning score.
  • Privacy: this gateway deliberately does not log drawings, audio, text, or credential values. Generated speech is returned to the device; there is no Firestore/Cloud Storage recording collection. Bhaasa keeps its normal local progress and audio saving behavior. Google’s API data-use policy depends on the project’s service/tier.
